A WorkBuddy Docker image for Computer Science work.

1. Introduction

This is a Docker image of the WorkBuddy agent with many packages for computer science works installed. It is intended as a pipeline for using AI for computer science research. For example, we can use Lean for mathematical proofs, TeX Live for writing papers in LaTeX, and Python 3 with many scientific packages pre-installed for experiments.

The image is based on our plain WorkBuddy image. It is intended for use in particular with rootless Docker installations. You can find the image at ghcr.io/thomasweise/workbuddy_cs.

WorkBuddy normally runs in a Chrome Sandbox. However, here we put it additionally into a Docker container. So it runs in a sandbox inside a container. This has the two advantages that we are (a) less likely to make errors that could mess up with our local data or systems configuration and (b) can have consistent installations of several tools directly contained in the image. (We did have to weaken the inner sandbox in some places to make it work, as explained in the workbuddy_plain documentation, though, so this weakens point (a) a bit…)

Notice: I am totally new to using AI tools. Therefore, this is really a very very experimental setup. I cannot guarantee that it will work.

    • packages for machine learning, statistics, testing, symbolic computation, optimization algorithms: scipy, scikit-learn, scikit-image, xgboost, sympy, cmaes,
    • packages for AI, neural networks: tensorflow-cpu,
    • packages for data loading: defusedxml, pandas, openpyxl, odfpy, polars,
    • packages for network access: urllib3, certifi,
    • packages for software development, such as linters, type checkers: autoflake, bandit, dlint, dodgy, flake8, flake8-2020, flake8-absolute-import, flake8-bugbear, flake8-builtins, flake8-commas, flake8-comprehensions, flake8-docstrings, flake8-eradicate, flake8-length, flake8-mutable, flake8-pyi, flake8-pytest-style, flake8-use-fstring, mypy, pycodestyle, pydocstyle, pyflakes, pylint, pyrefly, pyroma, ruff, tryceratops, vulture,
    • documentation generation: sphinx, sphinx-autodoc-typehints, pygments, myst-parser, markdown, minify_html,

    • package, setup, and deployment tools: setuptools, testresources, twine, virtualenv, wheel, psutil, and
    • our own packages: pycommons, moptipy, moptipyapps.
  • Java OpenJDK and Maven for Java development,
  • a full TeX Live installation,

  • an Inkscape installation for vector graphics editing, and
  • GIMP and ImageMagick for pixel image processing,

Additionally, we have pre-configured several Python-based MCP actions:

3. Run the Image

You can either run this image via the provided script or manually. Either way, after starting the container, you can log in as described in Section 4.1. After that, you can use WorkBuddy as discussed in Section 4.2.

Connection Issues: If your internet connection is unstable, it may take a few attempts to download the image. The image is not small. This download issue only occurs during the first launch of the image (or if you update it later on). If you experience connection issues, you can combine the script-based execution with our tryForever.sh shell script.

3.1. Run it via provided Script

Under Ubuntu Linux, you can run the container with script workbuddy_cs_run.sh. This script will take three optional parameters:

  • The directory to mount into WorkBuddy, by default "/tmp/workbuddy". This folder will be created if it does not exist. You can point this to some folder with data in it that you want to share. The default setting just uses a temporary folder, where nothing important should be in. This directory should have reading and writing permissions for the container. The easiest way to do this is to chmod 777 directory. The files created by WorkBuddy will have read permissions for you only, so you can tell it to give all files read/write permissions for everyone.
  • The version of the image to run, by default "latest"
  • The mode of the image to use. By default, this uses the image ghcr.io/thomasweise/workbuddy_cs from the GitHub package repository. If you set this to "local", then you can also run a Docker image that you built locally using, e.g., the scripts workbuddy_cs_build.sh and our Dockerfile.sh.

3.2. Run it by Hand from the Shell

Alternatively, you can run the image by hand. This will also download the image if it is not downloaded yet.

Notice that in order to run the image properly, you need to first set xhost +local:docker on your system. This is needed so that WorkBuddy can access your screen. You would do something like 

xhost +local:docker

docker run -it --rm \
  --name workbuddy \
  --network host \
  --cap-add SYS_ADMIN \
  -e DISPLAY=$DISPLAY \
  --add-host=update.codebuddy.cn:127.0.0.1 \
  --add-host=update.workbuddy.cn:127.0.0.1 \
  -v /tmp/.X11-unix:/tmp/.X11-unix \
  -v /path/to/folder/you/want/to/mount/into/image:/home/user/workbuddy-data \
  "ghcr.io/thomasweise/workbuddy_cs:latest"

4.3. Using the Computer Science Tool Chain

Now let's do a more advanced example. We will ask WorkBuddy to prove that 1+x <= exp(x) for all real-valued x. We will ask it to draw the two functions into a diagram next to each other. We will ask it put all the proof, description, maths, artifacts, and plots into one LaTeX document and compile it to PDF.

During the course of the example, WorkBuddy created the following files:

  • proof.lean
  • proof_results.txt
  • plot.py
  • plot.pdf
  • summary.tex
  • summary.pdf

If you read summary.pdf, you will find that the proof that it created does make sense. All the files are of surprisingly high quality.
